# Озвучка текста книги (TTS) с подключаемыми модулями

> Статус: **Этап 1 реализован** (ядро + Piper + espeak, хоткеи, индикатор, `:tts*` команды).
> Цель: дать tabook возможность читать книгу вслух голосом через **подключаемые
> TTS-модули** (бэкенды), чтобы подключать любые языки и любые движки —
> локальные (offline) и облачные.

---

## 0. Резюме

- Команда озвучки позволяет «читать с текущей позиции» страницу/абзац/главу голосом.
- Звук синхронизирован с **позицией в книге** (`charOffset`), так что прогресс чтения,
  навигация, закладки и возобновление после перезапуска работают как обычно.
- TTS разбит на **независимые бэкенды** (модули). У каждого бэкенда один и тот же
  интерфейс, поэтому движок и язык переключаются конфигом/командой без пересборки.
- На первом этапе поставляются 2 встроенных бэкенда: `piper` (локальный, рус. + др.) и
  `espeak` (локальный fallback). Остальные (Silero, Kokoro, Edge/MS, Chatterbox,
  любой внешний HTTP API) — по тому же контракту, как «внешние модули».
- Воспроизведение идёт через PipeWire/PulseAudio (`aplay`/`paplay`), как принято в Linux-TUI.

---

## 1. Контекст и цели

### 1.1 Зачем

tabook — терминальный ридер FB2/EPUB. Пользователь хочет слушать текст голосом
(«audiobook-режим») при сохранении всех возможностей ридера: навигация по главам,
позиция, закладки, поиск.

### 1.2 Почему «модули», а не один движок

- Языки книг разные (русский, английский, …); качество голоса у движков сильно различается
  по языкам.
- Нет одного «лучшего» движка: Piper — лёгкий и оффлайн, Silero v5 — лучший русский на CPU,
  Kokoro — отличный англоязычный, Edge/MS — студийное качество, но требует сети.
- Пользователь должен выбрать сам: `tts.engine` меняет голос без пересборки и без правок
  десятков мест в коде. Один интерфейс → много бэкендов.

### 1.3 Принципы

1. **TTS — отдельный слой, не вплетён в рендеринг.** Ядро ридера не знает про TTS;
   TTS-слой снаружи дёргает только публичные методы `ReaderSession` и `layout`.
2. **Бэкенд = модуль.** Контракт фиксирован (`interface TtsBackend`), реализация
   инкапсулирует «как синтезировать». Добавление языка/движка = новый файл-модуль.
3. **Звук не блокирует UI.** Синтез и воспроизведение идут в фоне; ридер остаётся
   отзывчивым (паттерн внешних процессов как у `imageLayer`).
4. **Корректный fallback.** Нет движка → аккуратная ошибка в статус-баре, не крах.
5. **Лицензионная чистота.** Выбор движка — за пользователем; встроенные бэкенды только
   со свободными лицензиями (MIT/GPL для личного использования достаточно).

## 2. Контракт TTS-модуля

Весь TTS-функционал сконцентрирован в новом каталоге `src/tts/`. Ядро определяет
интерфейс и менеджер; каждый движок — свою реализацию.

### 2.1 `src/tts/types.ts` — публичные типы

```ts
/** Один синтезируемый фрагмент текста вместе с его положением в книге. */
export interface TtsChunk {
  /** Чистый текст (без стилей/разметки), отправляемый в синтезатор. */
  text: string;
  /** Позиция начала этого фрагмента в координатах книги (charOffset). */
  startChar: number;
  /** Роль строки/блока (heading/paragraph/...), можно для пауз/интонации. */
  role?: LineRole;
}

/** Состояние воспроизведения (для статус-бара). */
export type TtsStatus =
  | { state: 'idle' }
  | { state: 'playing'; currentChar: number; chunkIndex: number; total: number }
  | { state: 'paused'; currentChar: number }
  | { state: 'error'; message: string };

/** Способность модуля — что умеет (для списка/проверки доступности). */
export interface TtsCapabilities {
  /** Языки, которые бэкенд реально поддерживает (коды BCP-47: 'ru', 'en', ...). */
  languages: string[];
  /** Требует сеть? */
  offline: boolean;
  /** Умеет ли изменять скорость/высоту на лету при воспроизведении. */
  rateControl: boolean;
}
```

### 2.2 `src/tts/backend.ts` — интерфейс бэкенда

```ts
export interface TtsBackend {
  /** Логическое имя (совпадает с `tts.engine` в конфиге) и человекочитаемое. */
  readonly id: string;
  readonly label: string;
  readonly capabilities: TtsCapabilities;

  /**
   * Проверить доступность (бинарник/модель/сеть) ДО старта, чтобы дать
   * осмысленную ошибку. Возвращает сообщение, если движок нельзя использовать.
   */
  check(): Promise<string | null>;

  /**
   * Синтезировать чанк в WAV. Реализация сама отвечает за локальный
   * движок или облачный API. Возвращает WAV-буфер или путь к файлу (`WavSource`).
   */
  synthesize(chunk: TtsChunk, opts: TtsVoiceOptions): Promise<WavSource>;

  /** Освобождение ресурсов (kill дочерних процессов) — для shutdown. */
  dispose(): void;
}
```

Воспроизведение вынесено **отдельно** от бэкенда — это общий `AudioPlayer`
(`src/tts/player.ts`), чтобы любой движок использовал одну звуковую систему:

```ts
export interface AudioPlayer {
  play(source: WavSource): void;
  pause(): void;
  resume(): void;
  stop(): void;
  onCallbacks(cbs: AudioPlayerCallbacks): void; // onEnded / onError
  dispose(): void;
}
```

Опции голоса (`TtsVoiceOptions`): выбранный голос (`voice`), скорость (`rate`),
необязательный объект конфигурации провайдера (`provider`) для облачных бэкендов.

### 2.3 Менеджер `src/tts/manager.ts`

- Реестр бэкендов: `register(b): void` (встроенные регистрируются при старте;
  сторонние подключаются программно через публичный API).
- `resolveBackend(id): TtsBackend | null` (special: `'auto'` — первый подходящий).
- Очередь чанков + текущий индекс; статусы `idle/playing/paused/error`.
- `play(chunks, {engine, voice})`, `toggle()`, `pause()`, `resume()`, `stop()`,
  `onStatus()`/`onAdvance()` для индикатора и follow-режима.
- Фильтрует неозвучиваемые чанки (`isSpeakable`) — иначе движок падает.
- Координация с навигацией: follow-режим — на Этапе 2 (см. §8).

## 3. Интеграция с текущей архитектурой (по факту кода)

Все точки ниже — **существующие места**, куда TTS подключается, ничего не переписывая в ридере.

### 3.1 Источник текста — РЕАЛЬНЫЕ функции

Уже есть готовые методы, чтобы взять «чистый текст с позиции»:

| Что нужно                 | Где                                                       | Что даёт                             |
| ------------------------- | --------------------------------------------------------- | ------------------------------------ |
| Чистый текст блока        | `blockToPlainText(block)` (`src/renderer/blocks.ts`)      | текст без стилей/маркеров            |
| Текст около позиции       | `session.textNear(charOffset, length)` (`readerModel.ts`) | уже схлопнутые пробелы               |
| Глобальная позиция чтения | `session.charOffset()`                                    | координата в книге для синхронизации |
| Строки текущего экрана    | `session.viewportLines()` (`TextLine[]`)                  | роли строк → паузы/интонация         |
| Начало блока по индексу   | `layout.blockCharStart(blockIndex)`                       | границы чанка                        |

**Рекомендуемый источник для озвучки:** итерация по блокам текущей страницы/главы через
`blockToPlainText`, а для «читать с середины абзаца» — `textNear`. Позиция трекинга = `charOffset`.

### 3.2 Сборка «очереди озвучки» из страницы (пример)

```ts
// В TTS manager: сборка чанков текущего видимого/целого абзаца.
session.viewportLines()      // TextLine[] текущего экрана
  .map(l => ({ text: блок-текст по l.blockIndex, startChar: ..., role: l.role }))
```

Границы брать по `blockToPlainText(blocks[l.blockIndex])` и `layout.blockCharStart`.

### 3.3 Хоткеи — `KeyAction`/`dispatchReaderAction`

- Новые actions добавить в `KeyAction` union и `KEY_ACTIONS` (`src/config/defaults.ts`):
  `tts_play` (читать с текущей позиции), `tts_pause`/`tts_resume`, `tts_stop`,
  `tts_next_chunk`, `tts_prev_chunk`, `tts_follow` (следовать за звуком/за текстом).
- Обработчик — в `dispatchReaderAction` (`src/tui/reader/readerActions.ts`), получив
  `session` из контекста: вызвать `manager.playFrom(session.charOffset(), session)`.
- Биндинги по умолчанию в `DEFAULT_KEYBINDINGS` (напр. `v` play/toggle, `V` stop,
  `S` — если свободно; точные клавиши — на усмотрение и **не конфликтующие** с текущими).
- Подписи — в `actionLabel` (`src/tui/keymap.ts`), чтобы попали в `?` (help).
- Хинты — в `readerHint` (`readerActions.ts`), чтобы отражались в статус-баре.

### 3.4 Команды `:` и палитра

- Команды: `:tts` (toggle), `:tts stop`, `:tts voice [engine]/[language]`,
  `:tts engines` (список доступных), `:tts rate [0.5-2.0]`.
- В `runCommand.ts` — новый `case 'tts'` с разбором подкоманды.
- В реестр `COMMANDS[]` (`src/tui/commands.ts`) — записи, чтобы `:tts ...` попали
  в палитру `Ctrl+P` и `:help` с `screens: ['reader']`.

### 3.5 Конфиг — TOML `[tts]`

Добавлено в `Config` (`src/config/defaults.ts`) и документацию `docs/CONFIGURATION.md`:

```toml
[tts]
# active | disabled (по умолчанию disabled — никаких побочных процессов)
mode = "disabled"
# локальный бэкенд: "piper" | "espeak" | ...
engine = "piper"
# голос внутри движка (например ru_RU-... для piper)
voice = "ru_RU-irina-medium"
# скорость воспроизведения
rate = 1.0
# граница чанка: "paragraph" (по умолчанию) | "page" | "chapter"
unit = "paragraph"
# максимальные символы в одном чанке; длинные абзацы режутся по предложениям
max_chunk_chars = 2000
# следовать ли за звуком при прокрутке (читать дальше автоматически)
follow = true
# полный путь к бинарнику движка, если автопоиск его не нашёл (напр. venv piper)
command = ""
# пауза (мс) между чанками; 0 = бесшовно (prefetch, синтез следующего идёт параллельно)
inter_chunk_pause_ms = 0
```

Парсер (`src/config/config.ts`) валидирует типы, клампит `rate` в [0.25, 4],
`max_chunk_chars` в [200, 20000] и `inter_chunk_pause_ms` >= 0 с предупреждениями; неизвестные ключи `[tts]`
игнорируются. Все клавиши переопределяются через `[keybindings]`.

### 3.6 Статус-бар

- Расширить `StatusBarSection` (`defaults.ts`) значением `'tts'` и
  `StatusBarData` (`StatusBar.tsx`) полем `tts?: string`.
- Показывать: `▶ 3/42` (играет) / `‖ пауза` / `■` (стоп) / мигающую ошибку.
- Секция входит/не входит в сайд выбранным пользователем в `[statusbar]`, как остальные.

### 3.7 Жизненный цикл внешних процессов

Строго по паттерну `imageLayer.ts` и `open.ts`:

- `spawn` бэкенда (piper CLI) с ловлей `stderr` → в ошибку статус-бара;
- стоп/рестарт при смене движка или выходе из ридера (`dispose`);
- таймауты и `child.on('error')/on('close')` — чтобы зависший движок не «съел» процесс;
- никаких блокирующий вызовов в UI-цикле (pipe WAV через `aplay`, не `spawnSync` в рендере).

### 3.8 Новые модули — карта файлов (как реализовано)

```
src/tts/types.ts        типы (TtsChunk, TtsStatus, TtsCapabilities)
src/tts/backend.ts      interface TtsBackend + AudioPlayer + WavSource
src/tts/manager.ts      реестр бэкендов, очередь чанков, статусы
src/tts/player.ts       SystemPlayer: WAV → paplay/aplay/ffplay
src/tts/bincheck.ts     commandAvailable() — проверка бинарника в PATH
src/tts/chunking.ts     buildChunks() + isSpeakable() — сборка чанков
src/tts/piper.ts        бэкенд Piper (локальный, pip piper-tts + голоса .onnx)
src/tts/espeak.ts       бэкенд eSpeak NG (системный fallback)
src/tts/index.ts        createDefaultTtsManager() + реэкспорты
src/tts/*.test.ts       unit-тесты (менеджер, chunking, sanitize, контракт)
```

Сторонний движок = новый файл в `src/tts/` + регистрация в `index.ts`. Правок
ридера не требуется.

## 4. Встроенные бэкенды первого релиза

### 4.1 `piper` (рекомендуемый, offline, русский)

- Движок: `piper` (pip `piper-tts`, CLI `piper`), голоса `onnx` c HF.
- Русский: `ru_RU-*` голоса (по умолчанию `ru_RU-irina-medium`), англ. и др.
- Процесс: отдаём текст по stdin → получаем WAV → `paplay`/`aplay`.
- Зависимость: пользователь ставит `pipx install piper-tts` (или AUR `piper-tts`,
  или standalone-архив с releases rhasspy/piper) и скачивает голос. tabook их
  не тащит — только оркестрирует.

**Piper не входит в зависимости пакета.** В `PKGBUILD` он объявлен в
`optdepends`, потому что это тяжёлый нейросетевой движок (~100 МБ с
Python-зависимостями), а озвучка нужна не всем. `post_install` печатает
подсказку, `paru`/`yay` предлагают поставить его при установке.

**Что видит пользователь без piper.** `:tts` не бросает сырой `ENOENT` в
статус-бар, а печатает в уведомление инструкцию — иначе на секунду мелькнёт
ошибка и пропадёт:

```
piper not found — TTS engine not installed.

Install piper-tts:
  AUR:  yay -S piper-tts
  pipx: pipx install piper-tts

Then download a voice: :tts config → Voice → pick one (e.g. ru_RU-irina-medium)
```

Проверка движка (`TtsManager.check()`) выполняется **до** синтеза, поэтому
подсказка приходит сразу, а не после первого упавшего чанка. Движок
`espeak-ng` при этом продолжает работать — он есть в репозиториях Arch
и ничего доустанавливать не требует.

**Устойчивая установка.** venv/ pipx-установки привязаны к версии Python и
ломаются при обновлении системы (частый случай на Arch). Не зависящий от
Python вариант — standalone-архив `piper_linux_x86_64.tar.gz` с
https://github.com/rhasspy/piper/releases:

```sh
mkdir -p ~/.local/share/piper-tts
tar -xzf piper_linux_x86_64.tar.gz -C ~/.local/share/piper-tts
ln -s ~/.local/share/piper-tts/piper/piper ~/.local/bin/piper
```

Оба места (симлинк и распаковка) входят в автопоиск tabook.

**Автоопределение (без настройки).** Бинарь piper и файлы моделей ищутся по цепочке:

1. `[tts] command` — явный путь к бинарю в конфиге;
2. `TABOOK_TTS_COMMAND` — переменная окружения;
3. `piper`/`piper-speak` в `PATH`;
4. типичные venv: `~/.local/bin`, `~/.local/share/pipx/venvs/piper-tts/bin`,
   `~/.local/pipx/venvs/piper-tts/bin` (старый pipx), standalone-распаковка
   `~/.local/share/piper-tts/piper/piper`, `~/.venv/bin`, `.tts-venv/bin`
   (включая уровни вверх от запуска tabook).

Модели голосов ищутся в `~/.local/share/piper[/{voices,models}]`, `~/.config/piper`,
`~/piper-voices`, `~/tts-models`, `.tts-models/` и рядом с найденным бинарём;
переопределяется через `PIPER_MODELS_DIR`. Если короткое имя голоса
(`ru_RU-irina-medium`) разрешается в `.onnx` — берётся оно, иначе считается путём.

**Защита от падения движка.** Piper (Python) падает с traceback на тексте:

- содержащем control-символы/NUL → `sanitizeTtsText()` вырезает их;
- состоящем только из знаков препинания/пробелов (нет фонем — частый случай при
  старте озвучки с середины абзаца) → чанк отбрасывается по `isSpeakable()`.
  Оба фильтра работают на уровне менеджера, поэтому защищён любой бэкенд.

### 4.2 `espeak` (fallback, всегда есть в Arch)

- Движок: `espeak-ng` / `speech-dispatcher` (`spd-say`). Русский есть, качество роботизированное.
- Никаких моделей; работает без установки чего-либо сверх пакета из репозитория.
- Используется как запасной вариант, если piper не найден или нет нужной модели.

### 4.3 Расширяемость «любых языков/движков»

- Silero v5 (`silero` onnx, лучший русский на CPU) — бэкенд по тому же контракту;
- Kokoro (`kokoro-js`, npm, Apache-2.0, Node/CPU) — для англ. и др. языков без python;
- Chatterbox / Coqui XTTS / Edge-MS — как `remote.ts` (HTTP) либо локальный процесс;
- любой кастомный: пользователь задаёт в `[tts.providers.<name>]` команду или URL,
  и бэкенд `remote`/`command` вызывает её с текстом.
  Каждый = новый файл в `src/tts/`, регистрируется в `index.ts`. Язык книги выбирает голос
  автоматически по `capabilities.languages`.

## 5. Подключение сторонних модулей (вне «коробки»)

Реализованный путь — **нативный модуль**: `TtsManager` и `createDefaultTtsManager`
реэкспортированы из `src/index.ts`, embed-consumer может зарегистрировать свой
бэкенд программно:

```ts
import { createDefaultTtsManager } from 'tabook';
const mgr = createDefaultTtsManager();
mgr.register(mySileroBackend); // любой TtsBackend
mgr.play(chunks, { engine: 'silero', voice: { voice: 'ru', rate: 1.1 } });
```

Конфиг-провайдеры (`[tts.providers.<name>]` — движок строкой команды/URL без кода)
и каркас `remote.ts` для HTTP API — запланированы на Этап 3.

## 6. Поведение / UX

### 6.1 Запуск озвучки — два способа (со старта)

Озвучку можно начать двумя способами, оба — через `:tts` и хоткеи:

**A. С текущей позиции (toggle)**

- `v` или `:tts` → озвучка с того места книги, где стоит курсор ридера
  (`session.charOffset()`), до конца страницы/абзаца/главы (по настройке `tts.unit`).
- Повторный `v`/`:tts` → пауза/возобновление; `V`/`:tts stop` → остановка.

**B. Возобновление с сохранённой позиции (continue)**

- `:tts continue` → озвучка продолжается с последней **сохранённой** позиции книги.
- Позиция берётся из **уже существующего** прогресса чтения: tabook кладёт её в БД
  (`db.setProgress(bookId, charOffset, percent)` / `session.saveProgress()`). Нового
  хранилища не нужно — просто читаем `charOffset` из текущей записи книги.
- Отличие от A: A стартует «откуда стоишь» (можно не совпадать с сохранённым местом,
  если пользователь листал вперёд/назад), B продолжает с последнего сохранённого места.
- Совместимость: если пользователь вёл обычное чтение и закрыл книгу, при следующем
  открытии `:tts continue` заговорит ровно с того же места — «рассказчик» продолжает.

### 6.2 Основной поток воспроизведения

1. Старт (вариант A или B выше) → TTS manager собирает чанки от выбранной позиции.
2. Первый чанк синтезируется и играется; статус-бар показывает `▶` и прогресс чанка.
3. После доигрывания чанка — следующий; при `follow=true` ридер прокручивает текст за звуком
   (как KK-режим), `charOffset` = позиция текущего слова.
4. Навигация (скролл/страница/глава/поиск) автоматически **ставит на паузу** (или следует
   за пользователем — см. 6.4). Позиция сохраняется в библиотеке как обычно (`saveProgress`).

#### Гранулярность чанка: абзацы (по умолчанию)

- **Чанк = один блок книги** (абзац, заголовок, строка стиха, строка таблицы, …) —
  то, что уже есть в `Block[]`/`book.content`. Текст берём через `blockToPlainText(block)`.
- Естественная пауза на стыке абзацев; заголовки/эпиграфы — отдельные чанки (структура/тишина).
- **Старт с середины абзаца:** если начитали с позиции внутри абзаца, чанк = `textNear(charOffset)`
  до конца абзаца (границы — `layout.blockCharStart(blockIndex)` и длина из `blockToPlainText`).
- **Длинные абзацы режем по предложениям:** если абзац > `tts.maxChunkChars` (по умолчанию
  ~2000 символов, настраивается), бьём на под-чанки по границам `.!?…` (не ломая слово).
  Нужно и синтезу (стабильность/паузы), и онлайн-API (лимиты). У каждого под-чанка свой
  `startChar` → `follow`/пауза корректно указывают позицию даже внутри разбитого абзаца.
- Альтернативы (`page` / `chapter`) — опционально через `tts.unit`; абзац — дефолт.

### 6.3 Управление

| Действие                                | Клавиша (дефолт) | Команда                               |
| --------------------------------------- | ---------------- | ------------------------------------- |
| Играть/пауза с текущей позиции (toggle) | `v`              | `:tts`                                |
| Возобновить с сохранённой позиции       | —                | `:tts continue`                       |
| Стоп                                    | `V`              | `:tts stop`                           |
| Переключить follow-режим                | `F`              | `:tts follow`                         |
| Сменить движок/голос                    | —                | `:tts voice piper/ru_RU-irina-medium` |
| Список движков                          | —                | `:tts engines`                        |
| Скорость                                | —                | `:tts rate 1.2`                       |

Дефолтные клавиши проверены по текущим биндингам (`DEFAULT_KEYBINDINGS` в
`src/config/defaults.ts`): `v`, `V`, `F` **свободны**. `n`/`N` заняты поиском,
`g` конфликтует с `gg`, `space/enter/esc/[]` заняты — их не использовать.
Чанк-навигация (`:tts next`/`prev`) дефолта не имеет — на Этапе 2; пользователь
может задать клавишу сам через `keybindings`.

### 6.4 Режим «следовать за текстом/звуком»

- `follow=true`: ридер прокручивается под озвучку, ручной скролл ставит паузу.
- `follow=false`: звук играет независимо, ручной скролл не останавливает (видны оба).

## 6A. Индикация во время воспроизведения (обязательно)

Во время озвучки **обязательна видимая индикация** — пользователь всегда понимает, что
сейчас играет голос, что поставлено на паузу, и где в тексте находимся. Механизм анимации
и форма — в стиле уже существующего `Spinner` (`src/tui/components/Spinner.tsx`), который
использует **брайлевский шрифт** (`⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏`, `setInterval` 80 мс в Ink).

### 6A.1 Статус-бар: иконки состояний

Новая секция статус-бара `'tts'` (`StatusBarSection`/`StatusBarData.tts`) показывает:

| Состояние                        | Отображение (пример)                                                                            |
| -------------------------------- | ----------------------------------------------------------------------------------------------- |
| Играет                           | **анимированный брайль-спиннер** + номер чанка: `⠸ 3/42`                                        |
| Пауза                            | `‖` + позиция: `‖ 15%`                                                                          |
| Стоп                             | `■` (по умолчанию секция пуста, показывается только при активности/паузе)                       |
| Ошибка                           | `⏻ piper not found` (мигающий/акцентный цвет, в статус-баре это уже поддержано полем `message`) |
| Загрузка/синтез следующего чанка | спиннер + `⏳` / прогресс чанка                                                                 |

Секция входит/не входит в сайд по `[statusbar]` как остальные; скрывается при `idle`,
чтобы не шуметь в покое. Для играющего состояния дополнительно можно рисовать
мини-прогресс чанка/страницы.

### 6A.2 Компонент-анимация

- Новый лёгкий компонент `TtsIndicator` (по образцу `Spinner`): сам держит `frame` через
  `setInterval`, **не блокирует** рендер (состояние обновляется только у самого индикатора —
  React/Ink перерисовывает инкрементально, ридер остаётся отзывчивым).
- Кадры брайля — по аналогии с `Spinner`; интервалы ~80 мс (можно подстроить под скорость).
- Использует диагностические/акцентные цвета темы (`theme.colors.accent`, `statusBar`,
  `statusBarText`) — ничего нового в вёрстке не требуется.

### 6A.3 Индикация в тексте (follow / karaoke)

Опционально, но **сильно рекомендовано** (пункт «следовать за текстом»):

- Текущая озвучиваемая **строка** подсвечивается в тексте (обратная/акцентная подсветка
  строки, `highlight` у `StyledSpan` уже есть — см. `applyHighlights`/`getHighlights` в layout).
- При `follow=true` ридер прокручивается так, чтобы подсвечиваемая строка была видна
  (напр. по центру экрана — как режим «karaoke»).
- Постепенный (посимвольный) акцент внутри строки — на Этап 2–3 (требует точных меток
  слово→позиция, см. Открытые вопросы №3). На Этап 1 достаточно подсветки всей строки/чанка.

### 6A.4 Требования

- Анимация **не мешает** вводу/навигации (индикатор живёт отдельным компонентом,
  не перерисовывает весь буфер форсированно).
- При `idle` индикатор скрывается; при ошибке — информативное сообщение, а не «повисший» спиннер.
- Тест: unit — компонент-индикатор рендерит корректное состояние для `playing/paused/error`;
  по правилу AGENTS.md — проверка анимации в **живом терминале** (только там видно, что кадры
  реально меняются и не конфликтуют с индикацией чтения).

## 7. Требования к качеству, ошибкам и лицензиям

- **Нет движка/модели** → статус-бар сообщает «tts: piper not found — установи piper-tts
  или выбери espeak», ридер продолжает работать.
- **Зависший процесс** → таймаут, `kill`, ошибка; не вешает приложение.
- **Пауза при выходе** → `dispose()` останавливает все дочерние процессы (никаких
  «висящих» piper после `q`).
- **Лицензии:** встроенные бэкенды — свободные (Piper MIT/GPL для личного использования
  достаточно; espeak GPL). Доступ к movel/ядру — отдельно и документально. Пользователь
  сам выбирает движок, tabook лишь оркестрирует.

## 10. Подключение дополнительных движков: исследование и варианты

Раздел отвечает на вопрос «как подключить, например, silero» и сводит всё, что
проверено на практике (замеры — на этой машине, x86_64, CPU-only; RTF = wall/длительность
аудио, меньше — лучше).

### 10.1 Что уже позволяет архитектура

Контракт `TtsBackend` (`src/tts/backend.ts`) требует от движка только `id`, `label`,
`capabilities`, `check()`, `synthesize(chunk, opts) -> WavSource`, `dispose()`.
Плеер (`src/tts/player.ts`) умеет играть **только WAV** (буфер или файл) через
ffplay/paplay/aplay — то есть любой движок обязан отдать WAV, больше ничего не требуется.
Регистрация: `createDefaultTtsManager()` в `src/tts/index.ts`.

Узкие места, которые придётся трогать при добавлении **любого** нового движка
(сейчас они захардкожены под пару piper/espeak):

| Место                                       | Что мешает                                                  |
| ------------------------------------------- | ----------------------------------------------------------- |
| `src/tui/components/TtsConfigModal.tsx:200` | переключатель Engine циклит `piper → espeak → piper`        |
| `src/tui/components/TtsConfigModal.tsx:102` | подпись Pitch жёстко упоминает espeak                       |
| `src/tui/components/TtsConfigModal.tsx:210` | «Download voice» уводит в piper-пикер                       |
| `src/tui/runCommand.ts:206`                 | `:tts engines` печатает строку, а не список живых бэкендов  |
| `src/tts/manager.ts:144`                    | текст ошибки «(piper or espeak)»                            |
| `src/tts/index.ts:29`                       | `command` из конфига передаётся **только** в `PiperBackend` |
| `src/tts/voiceIndex.ts`, `voiceManager.ts`  | индекс голосов жёстко привязан к `rhasspy/piper-voices`     |

Хорошая новость: `config.tts.engine` — свободная строка (никакой валидации по списку),
`voice` — тоже строка, так что новый движок включается правкой `config.toml` без сборки.

### 10.2 Вариант A — конфиг-провайдеры (универсальный «движок-команда»)

Один бэкенд `src/tts/command.ts`, который берёт из конфига команду и превращает её
в движок: текст → stdin, WAV → файл/stdout.

```toml
[tts]
engine = "my-silero"

[tts.providers.my-silero]
command = "~/.local/share/tabook/tts/silero-tts.py"   # или sherpa-onnx-offline-tts
args = ["--speaker", "{voice}", "--out", "{out}"]
# text_mode = "stdin" | "arg"   ({text} в args)
lang = "ru"
```

Плюсы: ни одна строка TypeScript не меняется при добавлении движка; один и тот же
бэкенд покрывает silero, sherpa-onnx, kokoro-onnx, edge-tts, `espeak-ng`, любой
свой скрипт. Минусы: движок не появляется в модалке голосов, качество/скорость
не проверить заранее. **Это самый дешёвый путь и он снимает 80 % задачи.**

### 10.3 Вариант B — Silero отдельным бэкендом

Факты (проверено, `pip install silero` → 0.5.5, torch 2.14.1+cpu):

- Silero **требует PyTorch**: официального ONNX-экспорта нет (issue
  `snakers4/silero-models#334`, открыт 15.09.2026). Значит ни `onnxruntime-node`,
  ни Rust-`ort` для Silero неприменимы — только Python-процесс.
- venv с torch CPU занимает **1.1 ГБ**, модель `v5_ru.pt` (139 МБ) скачивается
  автоматически в `site-packages/silero/model` при первом запуске.
- Один запуск на чанк (как сейчас у piper): `load 2.3–2.5 с + synth`, RTF 0.42–0.87.
  То есть на абзац ~3 с задержки — как у piper сейчас, минус килограммы зависимостей.
- **Постоянный worker** (процесс живёт, модель загружена один раз, обмен JSON-строками
  по stdin/stdout): `load 2.5 с` один раз, дальше **RTF 0.06–0.08** — на порядок
  быстрее piper. Это главный аргумент «за»: качество русского + автоударение.
- API: `apply_tts(text, speaker, sample_rate, put_accent, put_stress_homo, put_yo,
put_yo_homo, stress_single_vowel, ..., return_ts)`. Параметра скорости **нет** —
  `rate` придётся реализовывать ресемплингом WAV; `pitch` недоступен.
- Голоса: `v5_ru` → `aidar | baya | kseniya | eugene | xenia` (плюс v4/v3 и CIS-наборы),
  значит `voice` для silero — это пара «модель/говорящий», а не имя файла.

Итог: бэкенд — это реально ~200 строк (worker + spawn + авто-поиск venv), но тянет
тяжёлый optional-зависимость и требует persistent-процесса, а не разового spawn.
Как **opt-in** движок для тех, кому важен русский голос, — оправдано.

### 10.4 Вариант C — sherpa-onnx отдельным бэкендом (рекомендую начать с него)

`sherpa-onnx-offline-tts` — один готовый бинарник на C++/onnxruntime, без Python:

- Прекомпакт: `sherpa-onnx-v1.13.8-linux-x64-shared.tar.bz2` — **26.9 МБ**
  (статическая сборка — 404 МБ; в AUR есть `sherpa-onnx` 1.13.8-1, но она собирает
  из исходников, так что для пользователя лучше prebuilt-архив).
- Один движок покрывает сразу много семейств моделей: VITS (в т.ч. MMS `rus`,
  coqui, mimic3, piper-конвертированные), Kokoro, Matcha, KittenTTS, PocketTTS,
  ZipVoice, SupertonicTTS. Списки моделей: <https://k2-fsa.github.io/sherpa/onnx/tts/all/>,
  сами модели — в release `tts-models`.
- Проверено: `vits-mms-rus` (109 МБ) — русский текст синтезируется, `--num-threads=4`
  даёт **RTF 0.70** (1 поток — 1.09). Для сравнения, piper на том же тексте — RTF 1.13–1.32.
- Управление: `--speed`, `--vits-length-scale` (rate), `--sid` (мультиспикер),
  `--num-threads`, `--provider cuda`, плюс `--config <file>` — то есть движок
  конфигурируется файлом, что естественно ложится на `[tts.providers.*]`.
- Минус по сравнению с silero: Silero-стиля автоударения нет (MMS/piper — без него),
  и «модель + говорящий» надо описывать путями, а не коротким именем.

### 10.5 Вариант D — ONNX внутри процесса (не рекомендую сейчас)

`onnxruntime-node` (301 МБ распакованного) или Rust-крейт `ort` убрали бы
субпроцесс, но: (а) Silero всё равно не экспортирован в ONNX, (б) AUR-пакет
tabook сейчас — тонкий bundle + один `.node`, и +300 МБ нативной зависимости
ломает его подход, (в) для Kokoro/MMS это дублирует функциональность
sherpa-onnx. Оставить как эксперимент.

### 10.6 Сравнение

| Вариант             | Зависимости                 | RTF (ru)               | Усилий в tabook        | Охват                                                |
| ------------------- | --------------------------- | ---------------------- | ---------------------- | ---------------------------------------------------- |
| piper сейчас        | piper-tts + .onnx           | 1.13–1.32              | —                      | 40+ языков, без автоударения                         |
| A: config-провайдер | нет (сам движок)            | как у движка           | ~150 строк + правки UI | любой CLI-движок                                     |
| C: sherpa-onnx      | бинарник 27 МБ + модель     | **0.70**               | ~250 строк             | VITS/Kokoro/Matcha/Kitten/Pocket/ZipVoice/Supertonic |
| B: silero           | venv 1.1 ГБ + модель 139 МБ | **0.06–0.08** (worker) | ~300 строк             | лучший русский, автоударение, 5 спикеров v5_ru       |
| D: onnx in-process  | 301 МБ npm / Rust ort       | ~0.5                   | много                  | только ONNX-модели (не Silero)                       |

### 10.7 Рекомендуемый порядок внедрения

1. **Вынести список движков в данные, а не в UI.** Добавить в `TtsBackend`
   необязательные `listVoices?()` и `applyVoice?()`, а `TtsConfigModal`/
   `:tts engines`/текст ошибки в `manager.ts` строить из `mgr.engines`
   (источник истины уже есть — `TtsManager.engines`). Это обязательный шаг для
   любого варианта: иначе каждый новый движок снова придётся вписывать руками.
2. **Вариант A (`command.ts` + `[tts.providers.*]`)** — самый быстрый результат:
   пользователь получает silero/kokoro/что угодно без кода. `command` из конфига
   начать передавать **выбранному** бэкенду, а не только piper.
3. **Вариант C (sherpa-onnx)** — первый «встроенный» движок: без Python, один
   бинарник, много моделей, русский проверен и быстрее piper в ~2 раза.
4. **Вариант B (silero)** — opt-in бэкенд с persistent-worker, если аудитории
   важен русский голос выше всего остального; сопровождается подсказкой
   `uv venv && uv pip install silero --torch-backend=cpu` в `check()`.

Общий инвариант для всех вариантов: WAV на выходе, `check()` до синтеза,
`dispose()`, убивающий процессы, никаких блокировок UI и никаких новых рантайм-зависимостей
в самом tabook.

## 11. Выбор движка в UI и пути к движкам (реализовано)

Раздел §10 исследовал варианты. Здесь — что реализовано в коде по итогам.

### 11.1 Движки выбираются из реестра, а не захардкожены

Раньше список движков был зашит в UI: `TtsConfigModal` циклил
`piper → espeak → piper`, `:tts engines` печатал захардкоженную строку, подпись
Pitch упоминала «espeak only», а `[tts] command` передавался **только** в
`PiperBackend`. Любой третий движок пришлось бы вписывать руками в пять мест.

Теперь единственный источник истины — реестр `TtsManager.engines`:

| Что                             | Где                                             |
| ------------------------------- | ----------------------------------------------- |
| Список движков в модалке        | `mgr.engines` → `TtsConfigModal` (`Engine ▸`)   |
| `:tts engines`                  | `mgr.engines` + `mgr.check(id)` на каждый       |
| Текст ошибки «движок не найден» | `manager.ts` печатает реальный список доступных |
| Пути к движку                   | `configure()` у каждого бэкенда (§11.2)         |

Строка Engine открывает список с отметкой готовности (`ready` / `not installed`)
и командой установки для недоступного движка. Pitch/Rate теперь подписываются
по `capabilities` выбранного движка, а не по имени.

### 11.2 `[tts.engines.<id>]` — пути к движку и его голосам

Для движка, установленного не в PATH (venv, распакованный архив, нестандартный
префикс AUR-пакета):

```toml
[tts]
engine = "sherpa"

[tts.engines.sherpa]
command    = "~/.local/sherpa/bin/sherpa-onnx-offline-tts"  # полный путь к бинарю
models_dir = "~/.local/share/sherpa-onnx"                    # каталог с моделями
model      = "vits-mms-rus"                                  # голос по умолчанию
```

Пути раскрывают `~` и `$VAR`. Пустые секции при сохранении конфига не пишутся.
Неизвестные id движков сохраняются — пользователь может описать движок раньше,
чем мы его добавим. Общий `[tts] command` сохранён и работает как запасной вариант.

### 11.3 Новый бэкенд `sherpa` (`src/tts/sherpa.ts`)

Реализован вариант C из §10.4 — как «первый встроенный движок»:

- Установка: `yay -S sherpa-onnx` либо prebuilt-архив
  `sherpa-onnx-v1.13.8-linux-x64-shared.tar.bz2` (26.9 МБ, без Python).
- Один движок покрывает VITS (в т.ч. MMS `rus` и конвертированные из piper),
  Kokoro, Matcha, KittenTTS, ZipVoice, Supertonic.
- Русские модели: `vits-mms-rus.tar.bz2`, `vits-piper-ru_RU-irina-medium.tar.bz2`
  из <https://github.com/k2-fsa/sherpa-onnx/releases/tag/tts-models>.
- `rate` работает нативно через `--speed` (у VITS), в отличие от piper.

Особенности CLI, важные для реализации (проверено по исходникам
`sherpa-onnx/csrc/sherpa-onnx-offline-tts.cc`):

- текст передаётся **единственным позиционным аргументом**, не через stdin;
  второй позиционный аргумент — ошибка;
- отсюда `sanitizeForCli()`: вырезает управляющие символы, схлопывает переносы
  строк и **не даёт тексту начаться с `-`**, иначе sherpa примет его за флаг;
- модель — это каталог (`tokens.txt` + `.onnx`, у piper-моделей ещё
  `espeak-ng-data/`), поэтому `listVoices()` ищет каталоги, а не файлы;
- `summarizeSherpaStderr()` снимает адрес исходника (`file.cc:Func:38 …`) и
  выбирает конкретную причину, а не общее «Errors in config!».

Проверено вживую на этой машине (4 ядра, CPU-only), русский текст,
`vits-mms-rus`: RTF 0.63 при `--num-threads=4` (1 поток — 1.00).

### 11.4 Про Soprano: сознательно не подключён

Проверено по upstream (октябрь 2026):

- **только английский язык** — «Soprano is currently English-only and does not
  support voice cloning», многоязычность стоит в Roadmap, а не released;
- CLI перезагружает модель на каждый вызов (это прямо сказано в README), то
  есть та же задержка ~3 с на чанк, что у piper сейчас;
- ONNX-порт (`KevinAHM/soprano-web-onnx`) — браузерная демка на
  onnxruntime-web, не Linux-CLI.

Для русского FB2-ридера это не даёт выигрыша, поэтому отдельного бэкенда нет.
Когда Soprano станет мультиязычным, его можно подключить тем же способом, что
и остальные: новый файл в `src/tts/` + регистрация в `index.ts`.

### 11.5 Про Silero

Не реализован (нужен torch/venv ~1.1 ГБ и persistent-worker). Но учтено
главное из §10.3: задержка на чанк сейчас определяется **не синтезом, а
загрузкой модели** — на этой машине piper тратит ~3.0 с на запуск и синтез
одного слова, ~3.2 с на абзац. Отсюда вывод для любого будущего движка:
постоянный worker выгоднее смены движка.

### 11.6 Как добавить свой движок (после этих правок)

1. Новый файл в `src/tts/`: реализовать `TtsBackend` (минимум —
   `id`/`label`/`capabilities`/`check()`/`synthesize()`/`dispose()`).
2. Необязательно: `configure(paths)` — пути из `[tts.engines.<id>]`,
   `listVoices()` — локальные голоса для UI, `installHint()` — подсказка
   «как поставить».
3. Зарегистрировать в `src/tts/index.ts` — он сам появится в модалке,
   в `:tts engines` и в списке доступных движков. Правок ридера не нужно.
